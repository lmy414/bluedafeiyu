# 后台运维

本文面向服务器维护者，说明蓝色大肥鱼后台的安装、发布、Hermes 接入、备份和回滚。后台代码在
`admin/`，目标环境是 Debian/Ubuntu、Node 22、systemd 和 nginx。

后台和公开静态站分离。后台只监听 `127.0.0.1:3100`，公开站的 `/api/` 投稿服务不受影响。

## 1. 目录与账户

建议使用下面的固定结构。本文其余命令都按这个结构写。

```text
/srv/apps/dafeiyu-admin/
  src/      站点仓工作树（发布执行器/运维脚本；后台不在这里构建）
  releases/ 每次后台发布一个 release
  app/      当前 release 的软链
  data/     SQLite 数据库
  media/    后台预览素材（只存 webp 预览）
  run/      publish.request 等运行文件
  logs/     后台部署日志

/srv/www/dafeiyu/
  bluedafeiyu/ 站点与执行器源码工作树
  content/     图片内容仓工作树
  dafeiyu-intake/ 中转区与发布锁
  shared/data/ 静态站共享数据
```

创建账户：

```bash
sudo useradd --system --home /srv/apps/dafeiyu-admin --shell /usr/sbin/nologin dafeiyu-admin
sudo install -d -o dafeiyu-admin -g dafeiyu-admin /srv/apps/dafeiyu-admin/{src,releases,data,media,run,logs}
sudo install -d -o root -g dafeiyu-admin /srv/apps/dafeiyu-admin/releases
```

发布执行器以 `root` 运行，因为要执行部署脚本。`/srv/apps/dafeiyu/source` 与内容仓归 `dafeiyu`
用户，Git 操作使用 `sudo -u dafeiyu git ...`；后台服务用户不能读发布环境文件，也不能直接执行
部署脚本。若出现 root 属主文件导致 pull/稀疏检出失败，用
`chown -R dafeiyu:dafeiyu --from=root <dir>` 修复。

## 2. 后台环境

复制仓库里的模板并改成服务器自己的值：

```bash
sudo install -d -m 755 /etc/dafeiyu
sudo cp admin/.env.example /etc/dafeiyu/admin.env
sudo chown dafeiyu-admin:dafeiyu-admin /etc/dafeiyu/admin.env
sudo chmod 600 /etc/dafeiyu/admin.env
```

`/etc/dafeiyu/admin.env` 至少包含：

| 变量 | 说明 |
|---|---|
| `DATABASE_URL` | SQLite 文件路径，例如 `file:/srv/apps/dafeiyu-admin/data/admin.db` |
| `PAYLOAD_SECRET` | Payload 随机密钥，至少 32 字节；不要提交到仓库 |
| `PAYLOAD_PUBLIC_SERVER_URL` | 后台公开地址，用于 Payload 生成链接 |
| `ADMIN_WORKER_TOKEN` | 后台与发布执行器之间的 Bearer 令牌 |
| `ADMIN_PUBLISH_REQUEST_DIR` | 请求目录，systemd 默认使用 `/srv/apps/dafeiyu-admin/run` |
| `MEDIA_DIR` | 后台素材目录；只存 webp 预览 |
| `SUBMISSION_ADMIN_API_URL` | 投稿服务管理口，例如 `http://127.0.0.1:8788` |
| `SUBMISSION_ADMIN_TOKEN` | 投稿服务管理口令牌 |

修改后重启：

```bash
sudo systemctl restart dafeiyu-admin.service
sudo journalctl -u dafeiyu-admin.service -n 100 --no-pager
```

## 3. 安装 systemd 单元

仓库提供三个单元：

- `ops/systemd/dafeiyu-admin.service`：后台 Next/Payload 服务；
- `ops/systemd/dafeiyu-admin-publish.path`：监听 `publish.request`；
- `ops/systemd/dafeiyu-admin-publish.service`：执行发布请求，oneshot、root。

安装：

```bash
sudo install -m 644 ops/systemd/dafeiyu-admin.service /etc/systemd/system/
sudo install -m 644 ops/systemd/dafeiyu-admin-publish.service /etc/systemd/system/
sudo install -m 644 ops/systemd/dafeiyu-admin-publish.path /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable dafeiyu-admin.service
sudo systemctl enable --now dafeiyu-admin-publish.path
```

`.path` 单元发现 `/srv/apps/dafeiyu-admin/run/publish.request` 后启动 service。执行器会先把请求改名为
`publish.request.<runId>.taken`，所以同一个请求不会被 path 单元重复执行。

## 4. 发布执行器

执行器的环境文件是 `/etc/dafeiyu/admin-publish.env`。模板见
`ops/admin/admin-publish.env.example`。它复用 `ops/publish-batch.mjs` 的发布锁、仓库检查、工具链、
部署和 `markPublished` 逻辑。投稿原图由执行器按 `submissionId` 从投稿服务管理口读取到内存，校验
sha256 后直接写入内容仓；后台 media 目录只存 webp 预览。

内容仓工作树（`PUBLISH_CONTENT_DIR`）使用 git 稀疏检出，不检出原图：

```bash
git sparse-checkout set --no-cone '/*' '!/dist/submissions/originals/' '!/blue-fish-originals/' '!/owner-picks/*.png'
```

执行器用 `git add --sparse` 提交新原图，推送后 `git sparse-checkout reapply` 把原图移出工作树；
已有派生图的作品不再需要原图（`tools/generate_image_derivatives.py` 只为缺派生图的作品读原图）。
原图下载链接走 GitHub Raw。推送成功后执行器释放投稿服务里的原图；每日 04:15 的
`dafeiyu-prune-originals.timer` 清理 14 天前仍未释放的原图。部署用内容仓
`/srv/www/dafeiyu/content` 同样稀疏检出（`ops/deploy-server.sh` 自动设置）。

必须提供的变量：

| 变量 | 说明 |
|---|---|
| `ADMIN_API_URL` | 默认 `http://127.0.0.1:3100` |
| `ADMIN_WORKER_TOKEN` | 与 `admin.env` 中的值一致 |
| `ADMIN_PUBLISH_REQUEST_DIR` | 默认 `/srv/apps/dafeiyu-admin/run` |
| `SUBMISSION_ADMIN_API_URL` | 默认 `http://127.0.0.1:8788`；只请求 `/api/v1/items/sub_[A-Za-z0-9_]+/raw` |
| `SUBMISSION_ADMIN_TOKEN` | 投稿服务管理口 Bearer token；执行器只用于读取原图 |
| `PUBLISH_SITE_DIR` | 站点仓工作树 |
| `PUBLISH_CONTENT_DIR` | 内容仓工作树 |
| `INTAKE_ROOT` | 私有中转区；同时用于发布锁 |
| `PUBLISH_REMOTE` / `PUBLISH_BRANCH` | Git 远程与站点分支 |
| `CONTENT_BRANCH` | 内容仓分支；省略时跟随站点分支 |
| `PUBLISH_NODE` / `PUBLISH_PYTHON` | Node 与带 Pillow 的 Python |
| `PUBLIC_TURNSTILE_SITEKEY` | 公开 sitekey；写在 `/etc/dafeiyu/deploy.env` 与 `/etc/dafeiyu/admin-publish.env`，构建时注入投稿表单 |
| `PUBLISH_DEPLOY_ROOT` | `deploy-server.sh` 副本目录 |
| `DEPLOY_ROOT`、`REPO_URL`、`HEALTH_URL`、`CONTENT_REPO_URL`、`CONTENT_DIR`、`SHARED_DATA_DIR` | 传给 `deploy-server.sh` 的变量 |

安装：

```bash
sudo cp ops/admin/admin-publish.env.example /etc/dafeiyu/admin-publish.env
sudo chmod 600 /etc/dafeiyu/admin-publish.env
sudo systemctl daemon-reload
```

手动重跑一个已知的 runId（请求文件必须仍在 `ADMIN_PUBLISH_REQUEST_DIR` 中）：

```bash
sudo ADMIN_PUBLISH_REQUEST_DIR=/srv/apps/dafeiyu-admin/run \
  node /srv/apps/dafeiyu-admin/src/ops/admin/publish-worker.mjs --run <runId>
```

执行器只在 stdout 打印一行 JSON：

```json
{"runId":"...","status":"succeeded","summary":{"added":1,"updated":0,"hidden":0,"restored":0,"deleted":0,"topics":0},"commits":{"site":"...","content":"..."},"releasePath":"/srv/www/dafeiyu/releases/...","error":null}
```

失败时会写 `INTAKE_ROOT/batches/<runId>.json`。下次运行时只回收该 journal 记录过的路径；白名单外
的改动一律拒绝，不会自动 `git reset` 掉。

## 5. nginx

把 `ops/admin/nginx-admin.conf` include 到现有站点 `server { ... }` 块中。片段负责：

- `/admin`、`/cms-api` 反代到 `127.0.0.1:3100`，关闭缓存；
- `/_next/static/` 长缓存，其他 `/_next` 关闭缓存；
- `client_max_body_size 32m`；
- 不占用现有 `/api/` 前缀。

检查并重载：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## 6. 后台发布

后台构建只在 GitHub Actions 完成，服务器禁止跑 `next build`。推送 `admin/**` 到 `main` 或
`feat/admin-console`（或手动 `workflow_dispatch`）会触发 `.github/workflows/admin-build.yml`：

1. Ubuntu 24.04 + Node 22 执行 `npm ci`、`npm run build`；
2. 组装 `.next/standalone`、`.next/static`、可选的 `public/`，以及编译后的 `migrations/` 和
   `migrate.mjs`；
3. 在临时空库上跑迁移并启动 standalone 做 `/admin/login` 与 `/cms-api/users/me` 冒烟检查；
4. 生成 `admin-<短sha>.tar.gz` 和 `.sha256`，发布为 tag `admin-<短sha>` 的 prerelease，同时把
   同一对附件更新到固定 tag `admin-latest-<分支名去斜杠>`。

Windows 本机构建出的 standalone 会带 win32 原生模块，GitHub Actions 构建的是 Linux 原生模块。
生产服务器只能使用 CI 产物；不要把 Windows 机器的 `.next/standalone` 传到服务器。

首次安装顺序：

```bash
# 1) 按第 1-3 节建目录、写 /etc/dafeiyu/admin.env、安装 systemd 单元并 daemon-reload
# 2) 服务器已替 lmy414 登录 gh，先确认：
gh auth status --hostname github.com

# 3) 从指定 Release 首次部署（不写 tag 时脚本自动取最新 admin-<sha> prerelease）
sudo ADMIN_REPO=lmy414/bluedafeiyu \
  ADMIN_RELEASE_TAG=admin-<短sha> \
  bash /srv/apps/dafeiyu-admin/src/ops/admin/deploy-admin.sh

# 4) 首次健康检查通过后启用服务
sudo systemctl enable dafeiyu-admin.service
```

脚本按固定顺序执行：`flock` 防并发 → `gh release download` 到临时目录 → 校验 `.sha256` → 解压到
`releases/<tag>-<时间>` → 确保 `data/`、`media/`、`run/` 属于 `dafeiyu-admin` → 用
`sqlite3 .backup` 备份数据库到 `data/backups/admin-<时间>.db` 并只保留最近 10 份 → 以
`dafeiyu-admin` 执行 `node migrate.mjs` → 原子切换 `app` 软链 → 重启
`dafeiyu-admin.service` → 检查 `http://127.0.0.1:3100/admin/login` 返回 200。任一步失败都不切
新 release；重启或健康检查失败会把 `app` 切回旧软链并重启旧服务。服务器不会执行 `npm ci`、
`npm run build`、`npx payload` 或任何源码构建。

迁移入口 `migrate.mjs` 使用包内 `.next/standalone/node_modules` 的 Payload 和
`@payloadcms/db-sqlite`，构造最小 Payload 配置后调用 `payload.db.migrate()`；迁移文件是 CI 阶段
从 `admin/src/migrations/*.ts` 编译出的 JS，不依赖服务器上的 TypeScript/tsx。`DATABASE_URL` 必须是
绝对 `file:` 路径，例如 `file:/srv/apps/dafeiyu-admin/data/admin.db`；数据库、媒体和运行目录仍由
`/etc/dafeiyu/admin.env` 指向，不放进 release。

生产环境默认加载 `/etc/dafeiyu/admin.env`。发布时不要把真实数据库地址、令牌或域名写进仓库。

## 7. Hermes 接入

Hermes 定时任务运行：

```bash
cd /srv/apps/dafeiyu-admin/src
node ops/admin/hermes-publish.mjs
```

需要先给 Hermes 注入：

| 变量 | 说明 |
|---|---|
| `ADMIN_API_URL` | 后台地址，默认 `http://127.0.0.1:3100` |
| `ADMIN_BOT_API_KEY` | 后台 bot 账号的 API Key |
| `ADMIN_SITE_URL` | 发布成功后摘要里显示的线上地址 |
| `ADMIN_PUBLISH_POLL_MS` | 轮询间隔，默认 15000 毫秒 |
| `ADMIN_PUBLISH_TIMEOUT_MS` | 最长等待，默认 3600000 毫秒 |

Hermes 任务的 cron 可沿用现有发布窗口，例如 Asia/Shanghai 时区的 `0 0,6,12,18 * * *`，并发设为 1。
如果还要先同步投稿，使用：

```bash
node ops/admin/hermes-publish.mjs --sync-first
```

脚本没有变更时静默退出 0，不打印内容。有变更时发起发布并轮询，成功时打印新增、修改、隐藏、删除、
专题数量、站点短提交和线上地址；失败时打印失败步骤和错误并返回非零。Hermes 把脚本 stdout 原样投递
到站长飞书私信即可；不要为没有输出的情况补发消息。

### Hermes QQ 适配器补丁

Hermes 容器 `hermes-webui` 的 `/opt/hermes/gateway/platforms/qqbot/adapter.py` 有三处本地补丁：
接收 `GROUP_MESSAGE_CREATE` 全量群消息、路由到群消息处理、去掉 `<@openid>` 前缀。容器升级会
丢失补丁；`ops/hermes/patch-qqbot-adapter.sh` 与 systemd 单元 `dafeiyu-hermes-qqpatch.timer`
会开机 2 分钟后检查，之后每 5 分钟检查并补齐，补上后重启容器。锚点对不上时不改文件，并按镜像
去重向飞书群告警一次。

安装：

```bash
cp ops/hermes/systemd/dafeiyu-hermes-qqpatch.* /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now dafeiyu-hermes-qqpatch.timer
```

手动检查：

```bash
ops/hermes/patch-qqbot-adapter.sh --dry-run
```

## 8. 后台账号

密码仅以 Payload pbkdf2 哈希存于后台 SQLite 数据库，无法找回，只能重置。重置前先用 `sqlite3 .backup` 备份数据库：

```bash
sqlite3 <db> ".backup <db>.bak-<日期>"
```

## 9. 备份

SQLite 不要直接复制正在运行的 `.db` 文件。使用 SQLite 的在线备份：

```bash
sudo install -d -m 700 /srv/backups/dafeiyu-admin
sudo sqlite3 /srv/apps/dafeiyu-admin/data/admin.db \
  ".backup '/srv/backups/dafeiyu-admin/admin-$(date +%F-%H%M%S).db'"
```

素材目录可以直接同步：

```bash
sudo rsync -a --delete /srv/apps/dafeiyu-admin/media/ /srv/backups/dafeiyu-admin/media/
```

备份至少保留数据库、media、`/etc/dafeiyu/admin.env` 和 `/etc/dafeiyu/admin-publish.env`。环境文件含
密钥，必须用 `chmod 600` 和受限目录保护。

## 10. 回滚

后台代码回滚优先复用发布脚本，指定旧 tag 即可。脚本仍会先备份数据库、执行该 release 的
`migrate.mjs`、原子切换 `app` 并做健康检查：

```bash
sudo ADMIN_REPO=lmy414/bluedafeiyu \
  ADMIN_RELEASE_TAG=admin-<旧短sha> \
  bash /srv/apps/dafeiyu-admin/src/ops/admin/deploy-admin.sh
```

Payload 迁移是向前执行的；回滚旧代码不会自动执行 `down` 或恢复旧 schema。若旧代码与已执行迁移
不兼容，先停服务并从 `data/backups/admin-<时间>.db` 恢复对应数据库，再切旧 release；不要把生产库
直接复制回灌正在运行的服务。

只切软链的手动兜底（不删除 release）：

```bash
sudo readlink -f /srv/apps/dafeiyu-admin/app
sudo ls -1 /srv/apps/dafeiyu-admin/releases
sudo ln -s releases/<旧 release 目录名> /srv/apps/dafeiyu-admin/app.new
sudo mv -Tf /srv/apps/dafeiyu-admin/app.new /srv/apps/dafeiyu-admin/app
sudo systemctl restart dafeiyu-admin.service
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3100/admin/login
```

公开静态站回滚仍使用 `ops/rollback-server.sh <release 目录名>`。后台回滚不会回滚已经发布到公开仓的
内容；如果发布内容也需要回滚，重新在后台修改并发布，或按现有站点流程切换 release。

## 11. 故障排查

| 现象 | 检查 |
|---|---|
| `/admin` 502 | `systemctl status dafeiyu-admin.service`；确认监听 3100、nginx 片段已 include |
| 写请求后不发布 | 检查 `dafeiyu-admin-publish.path` 是否 active，`run/publish.request` 是否存在 |
| 执行器拿不到锁 | 查看 `INTAKE_ROOT/logs/publish.lock`；确认没有旧发布在跑，再按陈旧阈值处理 |
| 工作树脏 | 查看 `git -C <repo> status --short`；只允许执行器白名单文件，未知改动先人工处理 |
| sha256 不匹配 | 投稿服务返回的原图与快照清单不一致；先检查投稿队列条目和快照 sha256，再重新生成 snapshot |
| 构建失败 | 先手动跑 `node tools/prepare_works.mjs` 和 `node tools/build_site.mjs --content-dir ... --out ...` |
| 部署失败 | 看 `journalctl -u dafeiyu-admin-publish.service` 和 `deploy-server.sh` 日志；脚本会自行回滚 current |
| QQ 群 @机器人无反应 | 先运行 `ops/hermes/patch-qqbot-adapter.sh --dry-run`，再检查 `systemctl status dafeiyu-hermes-qqpatch.timer` |
| 站内投稿 403 / 429 | 403：Turnstile 未通过或 secret/sitekey 不匹配；429：触发每 IP 每小时 10 次限流 |
| Hermes 没有消息 | 无变更本来就不输出；有变更时检查 bot API Key、后台 run 状态和 stdout 投递规则 |
| Health 不是 200 | 确认 `/admin/login` 可从服务器本机访问，再检查 Payload 数据库和迁移状态 |

排查时不要打印 `ADMIN_WORKER_TOKEN`、`PAYLOAD_SECRET`、`ADMIN_BOT_API_KEY` 或数据库密码。
