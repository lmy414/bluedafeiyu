# 前端组件库与增量构建

业务页面只组合站内组件。发布默认分析变化，复用未变化的产物。首次发布、公共资源变化或基线损坏时，构建器自动完整重建。

## 组件与样式

组件源码在 `frontend/src/components/`。供浏览器直接加载的共享组件在 `frontend/public/components/`。保留旧导入路径的文件只负责转发，实际实现仍归组件库维护。

页面文件放在 `src/pages/`，只写路由、数据与组件调用。页面不得添加原生 HTML 版式、CSS 导入、内联样式、任意类名或样式覆盖参数。缺少能力时，先扩展现有组件的参数和变体；职责不同的功能再新增组件。

颜色、字号、间距和圆角优先使用设计变量。现有公共 CSS URL 是组件库的兼容资源，归属登记在 `component-library.json`。新增样式放入组件目录；确需公开 CSS URL 时，必须登记所属组件。页面不能自行增加样式文件。

公开页面统一使用 `Archive.astro` 的 `archive refined` 外壳，不按路由切换设计版本。`ArchiveTheme.css` 是公开前端颜色的唯一维护入口，旧变量通过别名使用同一套颜色；基础字号、间距仍沿用 `tokens.css`。通用标题由 `PageHeading` 输出，说明文档按“标题与简介 → 分区导航 → 正文”排列。详情页保留作品或角色的专用内容结构。

角色主页按“角色介绍 → 真实数量 → 立绘设定 → 表情 → 完整作品 → 相关内容”排列。阅读层级参考 [Claude 娘专题预览](https://bluefish-claude-topic-preview.divinecarp10.chatgpt.site/)。内容来自正式档案，不复制参考页的样本数字和作品。没有立绘、设定或梗图时，省略对应区块。

`CharacterJourney.mjs` 按明确类型选择最多 3 件立绘、设定和 4 件梗图。这些代表作品不改变人工专题成员。所有图片卡复用现有作品卡渲染器，保留作品 ID、slug、许可、预览和真实详情链接。设定卡说明读取作品描述；英日说明通过 `native-content.mjs` 读取真实作品译文。封面名称和标签选项由 `native-archives.mjs` 使用同一作品译文更新。

新模块用 overlay 的 `sa` 显示来源作者，缺失时显示“原作者未标注”。`a` 是展示署名，可能来自投稿者。`a` 存在且与 `sa` 不同时，另列“投稿署名”，避免把投稿者当作原作者。两个姓名节点都沿用 `author-name` 翻译保护，标签通过三语文案生成。共享搜索索引同时收录 `sa`、`a` 和已有 `owners[].name`，保留原有分词、评分及跨字段关键词交集规则。

浏览器读取 `/archive-data/zh.json`、`/archive-data/en.json` 或 `/archive-data/ja.json`。`src/lib/client-data.mjs` 的 `clientArchiveData` 保留 `a` 和 `sa`，供同一搜索索引使用。只给完整档案 JSON 增加字段，无法修复浏览器端搜索。类型、作者名、作品文字和标签同时参与筛选；没有结果时可清除条件。性能检查继续使用既有压缩体积预算。

繁体角色主页通过 `native-content.mjs` 复用已加载的 `SiteLang.contentText` 和站内 OpenCC，转换封面名称、静态作品卡标题、设定说明和场景选项的可见文字。原作者与投稿署名保持原名，选项 `value` 保留检索键；作品链接继续使用既有语言路由。英语和日语仍读取真实作品译文。

`ArchivePage.astro` 为角色详情、类型子页和分页统一添加 `.character-page[data-brand]`，并在 `body` 上写入 `data-character-page` 与 `data-brand`。三类路由共用同一骨架，类型页和分页不再退回普通列表版式。包装发生在 SEO 内容生成之后；`PageComposition.mjs` 不再折叠角色介绍或删除代表作品。SEO 收录说明放在整页末尾，继续生成无 JavaScript 的下一页链接。

### 角色页统一骨架

`CharacterPage.css` 是 24 个角色唯一的布局来源，只消费品牌 token。骨架固定以下规则，品牌样式不得覆盖：

- 区块顺序：介绍 → 真实数量 → 立绘设定（01）→ 表情（02）→ 完整作品（03）→ 相关合集（04）→ 继续探索（05）。数据缺失时省略对应区块，其余区块位置不变。
- 首屏：两列 `minmax(0, 1.05fr) minmax(0, 1fr)`，文字在左、人物在右，最小高度 560 px，间距 36 px，内边距 40 px，人物高度 `clamp(340px, 36vw, 490px)`。
- 栅格列数：设定 3 列、表情 4 列、完整作品 4 列、相关合集 3 列。
- 区块节奏：`margin-block: 64px`；内容最大宽度 1320 px 并居中。
- 卡片：设定图高 290 px、表情 210 px、作品 220 px，卡片内边距 14 px。
- 断点：1440（加宽节奏）、1100（表情与作品 3 列并缩小图高）、760（首屏单列、设定改横向图文行、表情与作品 2 列、合集 1 列）、390、320（继续收紧间距与图高）。
- 作品控件：类型用一组标签（`.character-type-tabs`，由 `data-character-type` 驱动，不再重复出类型下拉），下面是**一行**控件——搜索输入框、创作方式、排序、顺序和「清除条件」。角色与类型下拉保留为隐藏状态，供 `archive.js` 读写筛选状态；`filter-select.js` 只增强未隐藏的下拉，不会为隐藏项生成按钮。其他归档页仍用 `Listing.mjs` 的完整筛选条。

`CharacterBrandTokens.css` 只发布视觉 token：`--brand-*` 的取值写在 `body[data-character-page]` 上，只有内容区（`main#main` 及其子元素）消费映射后的全站变量（`--paper`、`--ink`、`--muted`、`--line`、`--blue`、`--radius-*`、`--shadow` 等）。品牌底色与纹理画在 `main#main` 上，并通过 `border-image` 向外延伸盖住左右留白；内容列、邀请条和页脚都铺在同一块底色上，邀请条与页脚自身透明、改用品牌文字色和分隔线，不再出现被品牌色包围的浅色矩形。侧栏、顶栏和 `<main>` 之外的站点外壳保持默认配色。内容列统一带左右内边距（桌面 32 px、≤760 为 16 px），文字和卡片不会贴住色块边缘。角色页内容区不套带边框或圆角的整页卡片，首屏也不使用描边外框——区块之间用间距和品牌底色区分，边框只出现在作品卡、控件和标签等真正的卡片单元上。

### 2026-10-31 首屏装饰层与底部修复

装饰作用于整个首屏：`header.character-hero` 的第一个子元素是 `div.character-hero-decor`（`position: absolute; inset: 0; z-index: 0; overflow: hidden; pointer-events: none; aria-hidden="true"`），内含 `--wash--`（渐变/纹理）、`--shape--`（大块图形与官方标识水印）、`--accent--`（点缀）三层。`.character-info`（`z-index: 2`）、`.character-portrait`（`z-index: 1`）与 `.character-hero-strip`（`z-index: 2`）都在装饰层之上，首屏布局几何不变。大块图形只落在人物列、右上角与底边；文字列上方只保留低透明度渐变与 ≤6% 的网格/点阵纹理，正文对比度仍由验收脚本逐项复核。手机（≤760）保留渐变，隐藏大块图形与点缀。

python -m pip install Pillow numpy onnxruntime
python tools/prepare_character_portraits.py --content-dir "<内容仓目录>"
```

图片卡片和作者作品横栏通过 `workPreviewAttributes(slug)` 接入同一预览组件。普通点击图片或标题打开预览，预览内的「查看详情」进入现有作品页；真实 `href` 保留，供无 JavaScript、搜索引擎及浏览器链接菜单使用。收藏、分享、作者与角色链接维持独立操作。切换只使用当前网格或作者横栏中已显示的图片，关闭后恢复触发元素焦点且不改变列表地址、筛选与滚动位置。

图片卡片的占位宽高读取实际派生图。构建快照中的 `thumbSize` 和 `displaySize` 分别记录缩略图和大图尺寸，浏览器目录用 `p` 和 `v` 传递；原图的 `width`、`height` 和文件大小保持原值。历史记录缺少原图尺寸时，列表和预览仍能在图片加载前保留正确比例。

首屏瀑布流在网格组件输出后同步排列，复用 `Masonry.mjs` 中的最短列算法。后续模块负责追加内容、调整窗口及图片加载后的校准。卡片图片用记录的比例保留空间，避免懒加载图片先出现零高度；无 JavaScript 时保留普通网格和真实详情链接。

交互目录使用 `/archive-catalog/{zh,en,ja}.json`，把字段名集中存储一次，浏览器解包后继续使用原有作品对象。目录只携带搜索和下载需要的角色、类型和专题字段。旧的 `/archive-data/{zh,en,ja}.json` 保留对象格式，供仍在缓存旧脚本的页面读取；完整公开 JSON 和开放 API 沿用现有格式。

延迟渲染的组件要在工厂初始化时登记固定文案的翻译，不能等到正文渲染时才登记。否则公开词典可能早于正文生成，导致缓存页面缺少翻译。

活动目录读取 `data/events.json`，每一期记录独立的 ID、详情 URL、三语标题与摘要、封面、截止日期和状态（`current` / `archived`）。该文件由构建器直接读取，不混入图片或人工专题清单。新一期活动须同时提供对应的独立详情路由；归档时将状态改为 `archived`，保留原详情 URL 并更新回顾内容。`/events.html` 默认展示当期活动，无当期时展示往期目录；两个固定分页地址为 `/events/current.html` 和 `/events/archive.html`。目录卡片只承载每一期的归档入口，活动规则、作品展览与结果留在该期详情页。

```

## 增量构建

入口保持为 `tools/build_site.mjs`。Astro 固定为 7.3.5，启用原生增量静态构建。缓存放在 `.build/astro-cache/`，独立于 `node_modules`，安装依赖不会清空缓存。

```powershell
# 默认：分析变化，增量构建。
node tools/build_site.mjs --content-dir <内容仓目录> --out .build/site

# 分析发布影响，不渲染页面。
node tools/build_site.mjs --content-dir <内容仓目录> --out .build/site --plan-only

# 使用指定的上次成功产物。
node tools/build_site.mjs --content-dir <内容仓目录> --out .build/next --previous .build/site

# 忽略缓存，完整重建。
node tools/build_site.mjs --content-dir <内容仓目录> --out .build/site --full
```

`--force-clean` 只允许清理指定的旧输出目录，不表示完整重建。`--full` 才控制完整重建。

构建按以下步骤执行：

1. 检查组件规范，暂存数据，同步内容图片，生成权威快照。快照阶段由 `tools/work-image-integrity.mjs` 检查全部已发布作品，来源包括投稿、站长自选和首批 blue-fish。每件作品看缩略图和大图：两者可以互相回退；远端 URL 按远端图片处理，不当成本地文件；本地路径必须真实存在。缺图比例超过 1% 时，在写入 `site-data.json` / `site-data.js` 前中止构建。未超过 1% 时继续构建，日志列出全部缺图作品 ID，不截断。构建结束前检查最终发布目录里的 `components/image-placeholder.svg`，文件必须存在且非空。noop 和复用预构建产物（prebuilt）的发布同样检查，避免占位图本身 404。分享卡片遇到真实图片下载或解码错误会让构建失败，不再生成空图片框。只有少量明确的 `/components/image-placeholder.svg` 由脚本用 Pillow 光栅化成真实位图。本地缺图时脚本也不再下载线上同名文件，内容仓未同步就直接报错（issue #33）。
2. 比较源码、锁文件、构建环境、内容与图片摘要，并验证上次产物的哈希。
3. 计算页面的数据摘要。作品详情保留延迟模板，分析依赖时不渲染正文。相关推荐会重新计算候选与排序，新作品进入推荐后会更新对应页面。
4. Astro 根据页面数据摘要和模板依赖图决定重建范围。公共构建脚本、语言处理、公共资源或工具链变化时，保守地完整重建。`frontend/src/` 下任一 CSS 变化也完整重建（原因记为 `bundled-styles-changed`）：Astro 把组件样式打包成全站共用的带指纹样式文件，只重渲染部分页面会让复用的旧页面引用已删除的样式文件。
5. 重新本地化变化页面，复用其余语言版本。公开 JSON、Markdown、分享卡片、站点地图和 gzip 也同步处理。
   开放 API 由 `scripts/open-api.mjs` 按公开快照导出到 `open-api/v1/`，逐文件比较内容复用；全量清单和失效文件随同一发布一起切换。关于页的接口文档由 `OpenApiDocumentation.astro` 维护，三语文案在 `src/lib/open-api-copy.mjs`。单独生成 JSON 可用根目录 `npm run build:api`，不执行页面和图片构建。
6. 完整校验新发布目录。成功后才替换指定的本地输出或切换线上 `current`。

聚合页面保守地依赖整个公开目录，避免计数、分页和翻译漏更新。作品详情使用自身、所属专题、相关推荐及原始元数据的摘要。视频 JSON 作为外部内容读取，视频更新不会被误当成所有页面的模板源码变化。

侧栏作品总数作为独立的共享组件更新。新增或下架作品时，构建器在已复用的 HTML 中更新这个组件，保持服务端输出的数字正确，避免为一个导航数字重新渲染整站模板。影响清单通过 `sharedChanges` 记录这类更新。

输入与产物都没有变化时，构建器跳过 Astro、语言转换和分享卡片生成。原生缓存缺失时，Astro 会重建相应页面。成功发布基线缺失、产物损坏或运行环境变化时，构建器会记录原因并完整重建。

多语言审计仍检查整个发布目录。增量构建减少生成工作，不降低验收范围。`sitemap.xml` 复用未变化正文的 `lastmod`。作品页的简中、繁中、英、日四个语言条目都会输出 `image:image`/`image:loc`。图片优先用该作品的 `displayUrl`；展示图缺失或为占位图时，回退到同一作品的有效缩略图。图片地址统一为绝对 URL：站内路径使用 punycode 站点源，远端 URL 保持原样，最后做 XML 转义。共享占位图不写进 sitemap，非作品页不输出图片标签。分享卡片缓存同时检查图片内容、绘图脚本、字体和图标，避免仅按文件时间复用旧图。

## 发布与诊断

`ops/deploy-server.sh` 仍从 GitHub 拉取源码，在独立 staging 目录构建。构建失败保留当前发布；健康检查失败切回旧发布。

服务器用 `build-state/<发布目录名>.json` 保存成功基线。基线按发布目录关联，回滚后会选中对应版本。详细影响清单保存在 `logs/build-plan-<发布目录名>.json`。这两类文件权限为 `600`，不放进公开站点。

公开的 `/build-info.json` 只包含代码与内容提交、构建模式、数量和耗时。文件不包含凭据、私有路径或后台内容。

依赖安装会核对锁文件、Node 环境和已安装版本。条件匹配时复用，变化时执行 `npm ci`。后台发布前完成构建和完整审计，部署通过 `PUBLISH_PREBUILT_DIR` 复用已验证的产物。只有输入摘要、页面依赖和全部产物哈希一致时才复用；不匹配时改用正式发布基线构建。显式 `--full` 会忽略预构建产物。

构建环境摘要也覆盖公开构建变量、环境文件、Python、Pillow 和字体。摘要不保存环境文件的原文。部署保留旧页面可能引用的带指纹 CSS、JS，避免 CDN 中的旧 HTML 请求不到资源。

后台发布的“无变更”判断同时核对线上 `build-info.json` 中的代码提交与内容提交。清单已经推送但部署尚未成功时，重试会继续部署；部署成功后才回写作品状态。历史版本缺失或构建记录无法读取时，也会重新部署。

预检与正式部署默认要求实际构建文件系统至少有 2048 MiB 可用空间，可用 `BUILD_MIN_DISK_MB` 调整。检查覆盖代码、内容、预检输出和发布目录。目录处于独立挂载盘时，按该挂载盘检查，避免宿主盘仍有空间却发生 `ENOSPC`。

服务器可设置 `BUILD_FULL=1` 强制完整重建。未设置时使用增量模式。

为减少发布磁盘占用，服务器可通过 `SITE_REUSE_ASSETS=1` 复用旧发布中内容相同、权限为 `644` 的图片和字体。构建器只链接已核对内容的不可变文件；替换文件前先解除目标链接。新 HTML、脚本与样式独立生成。发布脚本只调整权限不符的文件，避免改动旧发布的文件元数据。

gzip 复用前会解压并比较原文。损坏或过期的压缩文件会重新生成。部署不会修改旧发布正文，也不会自动删除旧发布或失败任务的数据。

```powershell
npm --prefix frontend run test:incremental
npm --prefix frontend run test:incremental:integration
npm run test:frontend
node --test ops/tests/admin-publish-worker.test.mjs ops/tests/publish-batch.test.mjs ops/tests/build-resource-runner.test.mjs
```

集成测试在 `.build/` 下建立独立的小型站点，运行真实 Astro 构建。测试覆盖无变化、编辑、新增、下架、基线缺失和构建失败。编辑与下架产物会逐文件对比同一输入的完整构建。`SOURCE_DATE_EPOCH` 固定比较时使用的站点地图时间。

本地集成测试需要先准备完整的 `dist/`，并提供 Python 与 Pillow。Windows 可设置 `PYTHON` 为本机 Python 路径。测试记录保存在 `.build/incremental-integration-results.json` 与 `.build/incremental-integration/`。

Astro 的原生增量能力仍使用实验标记。升级 Astro 前应重新执行完整回归与产物一致性测试，不能只看构建命令是否成功。参考：[Astro 增量静态构建](https://docs.astro.build/en/reference/experimental-flags/incremental-build/)。

每次渲染前清空生成的 `frontend/out/` 工作目录，由独立的 `.build/astro-cache/` 恢复仍有效的路由。复制后再次按本次路由清单剔除过期 HTML，只保留有效路由和显式公开的静态页面，避免 Astro 恢复旧缓存时带回已下架页面。缓存目录保持不变，失败构建留下的页面不会混入新发布。目录传输中的 `.rsync-tmp/` 不参与构建、产物清单及语言审计。
