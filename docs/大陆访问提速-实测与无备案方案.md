## 1. 结论

**大陆访问慢的根因是源站出网带宽硬限速在约 1 Mbps。** 线路、备案、缺 CDN 都不是原因。

三条独立证据互相咬合，指向同一个结论：

| 实验 | 结果 | 说明 |
|---|---|---|
| 大陆主机 → 大陆镜像站（对照） | **42.3 MB/s** | 测点自身带宽与协议栈没问题 |
| 大陆主机 → 本站源站 | **0.17 MB/s** | 同一台测点，同一时刻，差 **250 倍** |
| 源站 → Cloudflare（出境对照） | **0.117 MB/s** | 不是“回大陆”这一段的问题，源站出境同样慢 |
| 源站三路并发 → Cloudflare | 0.088 + 0.022 + 0.018 = **0.128 MB/s** | 三路加总正好落在 1 Mbps 理论值上 |
| 源站**六路并发 → 四个不同目的地** | 0.088 + 0.024 + 0.021 + 0.019 + 0.011 + 0.000 = **0.141 MB/s** | 加到六路、换四个目的地，仍然不涨 |
| 源站 → Cloudflare 的 TCP 握手 RTT | **5.4 ms** | 同城级延迟（CF 边缘就在香港），却只拿到 124 KB/s |

最后一条是决定性的：**限速发生在源站自己这一侧，与对端是谁、走哪条路由无关。** 三路并发各自分到 1 Mbps 的话，合计该有 3 Mbps，实测合计正好等于 128.1 KB/s。这是**令牌桶限速**的典型特征（固定速率 + 短暂突发额度）；如果是“别人抢带宽”，合计会是一个随机数。

落到实处：**管道 128 KB/s，实测首屏（24 张缩略图 + HTML/CSS/JS）合计 1.24 MB，所以一个访客独占也需要约 9.5 秒**；而这 9.5 秒是全站共享的，5 个并发访客就是每人 45 秒起。这个数字与“大陆打开慢”的体感完全对得上。

**这条限制不必花钱也能绕开**：把字节从源站搬走就行，见 §3.0。

### 1.1 顺带修正一个观察

源站 `/proc/net/snmp` 显示 `RetransSegs / OutSegs = 1684 万 / 7279 万 ≈ 23%`，看着像“线路丢包严重”。但这是**果不是因**：

- 管道满了以后，令牌桶只能**丢弃**超额包（因为它没有队列可以排）；
- 丢包触发 cubic 退避，退避又让管道更吃不饱，形成反复的“冲高—丢包—退避”循环；
- 大陆侧同步测的那 5 次 1 MB 下载**客户端零重传**，而速率在 60～700 KB/s 之间乱跳，正是这个循环的样子。

所以拿 23% 重传去推“要换 CN2 GIA 线路”会走错方向。**先把带宽放开，再看重传率。**

### 1.2 网卡出网计数会“超过”限速值（一个差点推翻结论的假象）

复测时发现一个乍看会推翻结论的现象：同时 `cat /proc/net/dev` 采样，这台机器**空闲 12 秒的出网增量折合 413 KB/s（3.3 Mbps）**，远高于 1 Mbps。但它不是“没有限速”的证据：

阿里云的带宽限制在**宿主机侧（EIP / vSwitch）执行，超额直接丢弃**，而 guest 里的 `eth0` 计数器统计的是“交给网卡的量”，被丢掉的包照样计入。于是 guest 看到的 TX 可以远高于真正上线速率，多出来的部分在 TCP 层就是**重传**。这正好解释了 §1.1 那 23% 的重传，也解释了为什么宿主机 38 天累计 TX（117 GB）看起来远超限速值。

所以判断“是不是硬限速”要用**并发加总**，不能用网卡计数：

| 测试 | 结果 |
|---|---|
| 单连接 → Cloudflare | 125 KB/s |
| 三路并发 → **同一个**目的地（Cloudflare） | 65 + 41 + 13 = **119 KB/s** |
| 三路并发 → **三个不同**目的地（Cloudflare / 阿里云镜像 / 清华镜像） | 8 + 108 + 14 = **131 KB/s** |
| 空闲 20 秒网卡采样 | 118 KB/s |

三个不同目的地加总仍是 ~128 KB/s，才构成“硬限速”的判据：如果只是单条连接被限制，三路不同目的地应该加总到三倍。后来又加到**六路并发、四个不同目的地**，合计 141 KB/s，仍然不涨。

另一条独立证据把“拥塞”也排除了：源站到 Cloudflare 的 **TCP 握手只要 5.4 ms**（说明 CF 边缘就在香港、同城级），而在这条 5.4 ms 的链路上单流下载只有 **124 KB/s**。5 ms RTT 的路径上 TCP 本可以跑满几百 Mbps，除非存在**限速**或丢包；而客户端侧实测**零重传**，所以是限速。

### 1.3 元数据里的 200 Mbps 是“规格上限”，不是你的带宽

`max-netbw-egress = 204800` Kbps 容易读成“我有 200 Mbps”。实际上：

- **`max-netbw-ingress` 也是 204800**。一进一出都是同一个数，说明这两个字段描述的是**实例规格的能力上限**（规格书数字），不是这份实例实际被允许跑多少；
- 真正生效的限速值不在这台 guest 里，而在 guest 之外的公网出口（EIP / 公网带宽 / 共享带宽包那一层），所以 guest 里的 `eth0` 计数会“超过”它；
- 反过来推：如果实际配置真的是 200 Mbps，那六路并发换四个目的地就不可能稳定停在 141 KB/s。**实测行为本身就是“这个字段不是实际配置值”的证明。**

所以“峰值 200 Mbps”和“实际 ~1 Mbps”可以同时为真：前者是机型能力，后者是这台机器公网出口的实际限速。要知道后者是多少、配在哪一页，得看 **EIP / 公网带宽 / 共享带宽包** 的设置，而不是实例规格。

**但结论不依赖这个归因**：不管 1 Mbps 是配在计费套餐、EIP 还是别处，可观测的事实是这台机器的公网吞吐就是 ~1 Mbps，而 §3.0 的零成本方案正是绕开它：把字节交给边缘，让源站只发 HTML。

## 3. 无备案可选手段（按性价比排序）

排序原则：先动“收益 ÷ 成本”最高的，前一档没做之前不要做后一档。

### 3.0 零成本方案（先看这一档，不用花一分钱）

**不改计费方式也能解决大部分问题**：把字节从源站搬走，源站那 1 Mbps 只留给自己发 HTML/JSON（约 92 KB/页）。

| # | 动作 | 成本 | 为什么有用 |
|---|---|---|---|
| 1 | **Cloudflare 免费版前置（橙云）+ Cache Rules 把边缘 TTL 拉到 30 天 + 开 Tiered Cache** | ¥0，零代码 | 图片从 CF 边缘出，边缘**不共享那 1 Mbps**。全站被引用图片约 21 MB，源站冷启动灌满一遍约 2.7 分钟，之后长期接近 0 回源 |
| 2 | **发布后预热缓存**：把 deploy 脚本的健康检查扩成“遍历全部图片 URL 各请求一次” | ¥0 | 消除冷启动：下一个真实访客拿到的全是边缘命中，而不是等源站慢慢喂 |
| 3 | **只处理那 8 张动图**：限帧数 / 降帧率；列表里用静态首帧、点击再放动图 | ¥0，脚本 | 250 张缩略图里只有这 8 张超 200 KB，却占了约 4.5 MB。**首屏那张 565 KB 的动图缩略图砍到几十 KB，首屏立刻受益**。其余 242 张中位 33 KB，不用动 |
| 4 | **给 `site-data.js` 加 `?v=` 指纹** | ¥0，一行 | 62.6 KB 从“每次访问回源校验”变成一年 `immutable`，边缘缓存后源站彻底不出这块流量 |
| 5 | **（可选）giscus 改成滚动到可视区再注入** | ¥0 | 把详情页评论区的 0.68 s 连接开销推迟到用户真要读评论时。**GA 不动**（见 §2.4、§3.3） |
| 6 | **BBR + nginx 补默认值**（见 §3.5） | ¥0 | 在**丢弃式限速**下 cubic 会反复退避；BBR 能稳定贴住 1 Mbps 上限并降低排队延迟，本场景收益最大的一次内核调整 |

做完 1、2、4 三项，**单次访问真正落到源站的字节会从约 92 KB 降到约 8 KB**（只剩 HTML 本体；`site-data.js`、CSS、JS 全在边缘且一年不回源），在 1 Mbps 下约 0.1 秒。也就是说：即使这条出口永远是 1 Mbps，源站也不再是瓶颈了。这是“不改计费”能达到的上限。

> 顺带发现（**不是速度问题，别混进来**）：`dist/data/blue-fish/previews/` 里 4 个 GIF 合计 25.4 MB，**没有任何作品引用**，而同名内容还有体积小 3～10 倍的 webp 版本并存。这是导入流程留下的死重，值得清理，但要走内容仓的边界（`dist/data/` 由仓库外流程生成，服务器侧还有一份 `shared/data` 硬链接副本），别当成性能优化顺手删。

两个前提要先测：

- **大陆 ↔ CF 边缘的实际质量**。既有 CF 文档 §4 的双轨实测方法可以直接用；如果质量太差，这条路失效，只能回到 §3.1 或换别的 CDN。
- CF 免费版要求**全量接管 zone 的 NS**，大陆 DNS 解析会从现在的 10 ms 变差（用长 TTL 缓解）。

### 3.1 （有预算时）解除源站 1 Mbps 限制：唯一的数量级杠杆

| 项 | 内容 |
|---|---|
| 预期收益 | **100～200 倍**。按 §1 的实测，从 128 KB/s 提升到实例上限 200 Mbps（元数据已确认该规格支持 204800 Kbps） |
| 成本 | 控制台改一次计费方式，几分钟；不动代码、不动 nginx、不涉及备案 |
| 风险 | 低。**唯一风险是账单**：按流量计费下“有人刷你站”会变成真金白银，配合源站加固（见既有 CF 文档 §5.6）一起做 |
| 做法 | 阿里云控制台 → ECS → 实例 → 公网带宽 → 把“按固定带宽 1 Mbps”改为**“按使用流量”**，峰值带宽拉高（例如 100 Mbps）。单价以阿里云官网当时价为准 |
| 怎么估月费 | 先量当前月出网量：`sar -n DEV -f /var/log/sysstat/sa<日>` 取 `rxkB/s`+`txkB/s`，或对比两次 `/proc/net/dev`；再乘按量单价 |

**如果决定花钱，这是唯一值得花的地方。** 但 §3.0 已经能用零成本拿到大部分收益，所以顺序上先做 §3.0，这一步留到有余量时再补。

### 3.2 前置 CDN：在“源站被限速”的前提下，它比既有文档说的更有价值

付费的、**必须备案**的路（境内 CDN / 境内 OSS / 境内源站 / CF 中国网络）全部排除，剩下的选择：

| 选项 | 备案 | 对大陆的实际意义 |
|---|---|---|
| Cloudflare 免费版（`webp` 等默认缓存 7 天） | 不需要 | 缓存命中时**直接绕过带宽问题**：数据从 CF 边缘出，而边缘不限速。RTT 可能更差（大陆→境外边缘要多绕），但带宽从 1 Mbps 变成“够用”，净效果通常明显为正 |
| Cloudflare 付费（Argo 等） | 不需要 | 回源走 CF 骨干，缓解“边缘↔源站”那段 |
| 阿里云 CDN **海外**节点 / 又拍云 / 七牛海外 / Gcore / Bunny | 不需要 | 边缘在香港/日本/新加坡，作用是“加点缓存 + 分散带宽”；因为边缘和源站基本同城，RTT 收益有限 |

**要点：CDN 在这里解决的是带宽，不是延迟。** 大陆→香港这 50 ms 的 RTT 在不上备案源站的前提下是拿不掉的，所以不要用“CF 没让我 TTFB 变快”来否定它：它该拿的是吞吐。

配合既有 CF 文档实施时，那篇里的坑依然全部成立（别用 Flexible、Always Use HTTPS 先关、健康检查加 cache-buster、放行 CF 的 IP 段）。

### 3.3 第三方依赖（**低优先级，可选**）

实测这几项在大陆都能通（§2.4），**所以这里没有必须做的事**。只有在你想压掉那几百毫秒连接开销时才考虑：

1. **GA4：不动**（维护者决定）。它由国内 CDN 节点提供，不碰源站、不占带宽、统计正常。原先提议的“去掉 / 延后注入 / 换自托管统计”全部撤回。
2. **giscus（可选，非大陆特有问题）**：详情页的评论区离首屏很远，可以按通用做法改成**滚动到可视区域再注入**，把 0.68 s 的连接开销推迟到用户真的要读评论时。不做也不影响任何功能。
3. **原图下载（可选）**：`raw.githubusercontent.com` 实测 0.92 s 能通，只是境外。它只在点“下载原图”时请求，不在首屏，优先级最低。

### 3.4 继续省字节（在限额环境下等于免费加带宽）

| 手段 | 直接收益 |
|---|---|
| 给 `site-data.js` 加 `?v=<指纹>` | 从“每次访问回源校验 62.6 KB”变成一年 `immutable`。首屏少一次往返，也是全站最大的一块文本 |
| 4 张动图（`large` 最大 974 KB、`previews` 最大 581 KB） | 动图是 GIF 转的，动辄 0.5～1 MB。建议限制帧数/尺寸，或详情页改成“先出首帧，点击再加载” |
| 预览图 `srcset`（移动端给 240 px） | 移动端首屏图片字节大致减半 |
| AVIF（`<picture>` 里 avif + webp 回退） | 同质量比 WebP 小 20%～30%；4 张动图和 24 张首屏图都吃这个收益 |

### 3.5 源站 TCP / TLS 调优（零成本，做完 3.1 之后再评估）

现在 `cubic` + 令牌桶是最差的组合：桶满了就丢，cubic 见丢包就退避。换成 BBR 后更容易把管道吃满、排队延迟也更低。

```nc
# /etc/sysctl.d/99-bbr.conf
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
```

```bash
modprobe tcp_bbr
echo tcp_bbr > /etc/modules-load.d/bbr.conf
sysctl --system
sysctl net.ipv4.tcp_congestion_control          # 期望 bbr
cat /proc/sys/net/ipv4/tcp_available_congestion_control
```

这台机器同时在做中转/代理（`ip_forward=1`）。**改拥塞控制会同时改变代理流量的行为**，所以别顺手改，先说清楚这台机器上跑的是什么。

nginx 侧（都是补默认值里缺的，且不会重复声明已有指令）：

```nginx
ssl_session_cache shared:SSL:10m;   # 默认 off
ssl_session_timeout 1d;
ssl_stapling on;                    # 实测当前未启用
ssl_stapling_verify on;
ssl_trusted_certificate /etc/letsencrypt/live/<域名>/chain.pem;
resolver 223.5.5.5 119.29.29.29 valid=300s;   # stapling 需要 resolver
ssl_buffer_size 4k;                 # 小文件首字节更快出（默认 16k）
keepalive_requests 1000;
open_file_cache max=2000 inactive=60s;
open_file_cache_valid 30s;
open_file_cache_min_uses 2;
```

`sendfile on` / `tcp_nopush on` 全局已经是开的，不用动。`worker_connections 768` 偏小（2 核默认值），站点流量不大，优先级最低。

### 3.6 分线路解析（大陆直连、海外走 CDN）

阿里云云解析（万网，就是这个域现在用的 NS）免费版即带**电信 / 联通 / 移动 / 海外**线路细分（以控制台为准）。理想形态是：

```text
大陆线路  →  A 记录直连源站（RTT 最短，带宽放开后已经够快）
海外线路  →  CNAME 到 CF 代理的备用域名（省源站流量、抗攻击、加速海外）
```

有个结构性冲突：**CF 免费版要求全量接管 zone 的 NS**，而 zone 一旦迁到 CF，大陆的 DNS 解析也就跑到境外去了（当前万网解析实测只要 10 ms，迁走是**倒退**）。所以想同时要“分线路”和“CF 免费版”，只能用另一个域名承接 CF 那一路。如果海外访客占比很小，更简单的答案是**不上 CF**，把精力全放在 3.1。

### 3.7 明确不建议的

- **CF“优选 IP”/ 第三方优选域名**：本质是拿别人的 anycast IP 列表做灰产式优化，稳定性、合规性、可持续性都差，只适合当临时救急，不该进方案。
- **多节点 + 分线路自建**：每台海外 VPS 都要同步一份静态站，收益远小于 3.1，且在 1 Mbps 源站下毫无意义。
- **HTTP/3**：源站 nginx 1.24 不带 QUIC，要上得换 Caddy 前置或 nginx mainline 动态模块。**在带宽受限的前提下收益很小**（瓶颈不是握手），排最后。

## 4. 合规边界（不要越线）

| 想法 | 为什么不建议 |
|---|---|
| 境内 CDN / 境内 OSS 托管该域名 | **必须 ICP 备案**，且备案本身要求主体/源站在境内。这就是本方案的前提，不碰 |
| 用那台杭州服务器（`114.55.148.130`）反代中转本域名 | 域名解析仍在境外，但 Web 服务落在境内，属于**规避备案**。管局或云厂商查出后可能封 IP 或封账号，连带把面板和别的站一起拖下水 |
| 阿里云“全球加速 GA”精品线路 / 腾讯云同类 | **加入境接入点通常要求域名备案**，纯境外接入点不需要。要办之前先向阿里云确认清楚，别默认它免备案 |
| CF 中国网络 | Enterprise + 境内备案 + 京东云落地，个人站无门 |

**合法可走的路只有一条：境外/港澳源站 + 境外 CDN + 分线路解析 + 源站带宽充足。** 这也是本方案的全部内容。

## 7. 与《Cloudflare-CDN-配置方案.md》的一处冲突

那篇 §1 的结论是：**“CF 免费版能给这个站省钱、抗攻击、加快海外访问，但对‘中国大陆访客’基本不加速”**，理由是免费的 anycast 边缘没有大陆节点。

**这个结论在“源站带宽充足”的前提下成立，但在这台源站上不成立。** 瓶颈是源站只有 1 Mbps，不是多了一跳 RTT：

- 缓存命中时数据从 CF 边缘出，边缘**不共享那 1 Mbps**；
- 代价是多几十毫秒 RTT（50 ms → 可能 100～200 ms）；
- 用多几十毫秒换几十倍带宽，在大陆访客这里通常是**明显净赚**。

所以那篇可以保留（配置步骤、Flexible 的坑、ACME 的坑、real-ip 顺序、健康检查 cache-buster 全部有效），**只需要把 §1 的结论限定为“源站带宽不受限时”**，并把“§3 走不通的三条路”补上本方案 §3.1 这一条。

本文不修改那篇原文，改不改由维护者定。
