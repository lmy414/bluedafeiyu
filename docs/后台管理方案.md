# 后台管理方案

记录日期：2026-09-29。本文记录站长确认过的后台需求、数据口径和施工切片，是后台施工与验收的唯一依据。与代码冲突时，先改本文再改代码。

## 1. 已确认的需求

| 编号 | 需求 | 确认结论 |
|---|---|---|
| R1 | 数据真源 | 作品、角色、分类、专题以 Payload 数据库为准。发布时导出成 `data/*.json`，提交 Git，再沿用服务器拉取和原子发布。迁移完成后不再手改 JSON。 |
| R2 | 前后台分离 | 前台保持纯静态。后台只做管理和构建入口，改动要重新构建上线才生效。后台崩溃不影响前台，前台也不影响后台。 |
| R3 | 投稿审核 | AI 初审通过的投稿直接进入“待发布”，不需要人工点通过。站长只做“移除”和上线后的“复审”。 |
| R4 | 发布 | 站长在后台点“发布”，把所有待发布内容和改动一起发布。 |
| R5 | 专题 | 名称、简介、封面；从作品库搜索勾选作品；拖动排序；状态分草稿和上线。 |
| R6 | 多语言 | 专题名称与简介支持中文、英文、日文。前台按当前语言显示，缺英文或日文时回落中文。后台界面只做中文。 |
| R7 | 下架 | 分两种：隐藏和删除。隐藏：前台不可见，后台保留，可恢复。删除：彻底移除作品记录、图片和公开清单条目，只留防止重复收录的墓碑。 |
| R8 | 分类 | 作品可单个或批量改分类。 |
| R9 | 机器人 | 给 Hermes 开独立后台账号。Hermes 可以定时发布，发布后通过飞书通知站长。 |
| R10 | 移除 AstrBot | AstrBot 的审核路径下线，QQ 投稿改由 Hermes 审核。QQ 入站接口与来源无关，暂时保留，等 Hermes 接管 QQ 入站后再处理。 |
| R11 | 线上测试 | 用一条测试投稿在线上完整走一遍“投稿、审核、加入专题、发布、下架”，测试完下架，并记录在本文第 9 节。 |

## 2. 部署拓扑

```text
浏览器 ──Cloudflare──▶ Nginx（aliyun-hk）
                        ├─ /            静态站 /srv/www/dafeiyu/current（不变）
                        ├─ /api/        投稿服务 127.0.0.1:8790（不变）
                        └─ /admin /cms-api /_next   后台 127.0.0.1:3100（新增）

后台服务 dafeiyu-admin.service（用户 dafeiyu-admin，MemoryMax 限制）
  ├─ SQLite：/srv/apps/dafeiyu-admin/data/admin.db
  ├─ 素材：/srv/apps/dafeiyu-admin/media
  └─ 发布请求：写 /srv/apps/dafeiyu-admin/run/publish.request

发布执行器 dafeiyu-admin-publish.service（root，oneshot，由 .path 单元触发）
  导出 data/*.json → 写内容仓图片 → 派生图 → 构建校验 → 提交推送 → deploy-server.sh → 回写结果
```

- 后台只监听回环地址。Nginx 只把 `/admin`、`/cms-api`、`/_next` 三个前缀转给后台，其他路径不经过后台。
- 后台进程挂掉时，Nginx 只对这三个前缀返回 502，静态站不受影响。
- 发布执行器与后台进程分开：后台只写请求文件，Git 凭据和部署权限只在执行器里。
- 暂不开独立子域名：主域 DNS 在 Cloudflare，本机没有 DNS 令牌。以后要改成 `admin.` 子域名，只动 Nginx 和 Payload 的 `serverURL`。

## 3. 数据模型

### 3.1 作品 `works`

在现有字段上调整：

| 字段 | 说明 |
|---|---|
| `workId`、`slug` | 与现站一致，发布后冻结。新作品的 `workId` 为 `sticker_<sha256 前 24 位>`；`slug` 由发布时的 `tools/prepare_works.mjs` 生成，再回写后台。 |
| `kind` | `submission`（投稿）、`owner-picks`（站长自用）、`blue-fish`（首批档案）。 |
| `channel` | 投稿渠道：`web`、`github-issue`、`qq`、`manual`、`owner`、`blue-fish`。审核页按它筛选。 |
| `submissionId`、`sha256` | 关联投稿队列与去重。`sha256` 在投稿作品中唯一。 |
| `status` | `pending` 待发布，`published` 已上线，`hidden` 已隐藏，`removed` 已移除（未上线就移除），`deleted` 已删除（墓碑）。 |
| `needsPublish` | 公开字段有改动、尚未发布时为真。发布成功后清零。 |
| `lastPublishedAt`、`lastPublishRun` | 最后一次发布时间与批次。 |
| `review` | AI 审核结果（结论、置信度、理由、模型），只读。 |
| `legacyData` | 导入时的原始记录，导出时作为字段顺序与未知字段的基础。 |

状态流转：

```text
投稿 AI 通过 ──同步──▶ pending ──发布──▶ published ⇄ hidden（发布生效）
                         │                  │
                         └─移除─▶ removed    └─删除─▶ deleted（发布生效，图片清除）
AI 拒绝 / 转人工的投稿 ──站长“收录”──▶ pending
```

- `removed` 和 `deleted` 都保留 `sha256` 墓碑，同步时不再重复收录同一张图。
- 删除只有站长能操作，需要二次确认。删除在下一次发布时移除公开清单条目和内容仓图片，再清除后台素材。

### 3.2 专题 `topics`

| 字段 | 说明 |
|---|---|
| `topicId` | kebab-case，上线后冻结。 |
| `name`、`summary` | 中文，必填。 |
| `nameEn`、`summaryEn`、`nameJa`、`summaryJa` | 可选，缺省回落中文。 |
| `cover` | 关联作品，必须在收录作品内；缺省取第一张。 |
| `works` | 有序关联作品列表，拖动排序。 |
| `status` | `draft` 草稿、`active` 上线。 |
| `order` | 专题之间的顺序。 |

### 3.3 投稿 `submissions`

后台镜像投稿队列的全部条目（网页、GitHub Issue、QQ），只读展示渠道、原图、投稿字段、AI 结论和状态历史，并关联生成的作品。队列的真源仍是 `server/` 私有存储，后台不回写队列状态。

### 3.4 用户与机器人 `users`

| 角色 | 能做什么 |
|---|---|
| `owner` 站长 | 全部操作。删除只有站长能做。 |
| `bot` 机器人 | 用 API Key 访问。可读投稿、作品、专题；可改作品字段和分类；可发起发布。不能删除、隐藏、移除，不能登录后台界面，不能管理用户。 |

Hermes 使用账号 `hermes@bot.local`（`role=bot`）。它的操作全部写审计记录，`actor` 记为 `hermes`。

## 4. 导出口径

发布执行器从 Payload 生成下列文件，写法与现有文件逐字节兼容（字段顺序、两空格缩进、CRLF 换行、末尾换行）：

| 文件 | 内容 |
|---|---|
| `data/works.json` | `kind=submission` 且 `status=published` 的作品，按现有顺序。 |
| `data/owner-picks.json` | `kind=owner-picks` 且已上线的作品。 |
| `data/characters.json`、`data/categories.json` | 角色与分类词表。 |
| `data/topics.json` | `status=active` 的专题，字段见 3.2，另加 `i18n: { en: {name, summary}, ja: {name, summary} }`。 |
| `data/blue-fish-editorial.json` | 首批档案的编辑叠加层。隐藏或删除的首批作品在叠加层写 `status: "hidden"` 或 `status: "deleted"`，快照构建跳过它们。 |

`data/blue-fish-classification.json` 与 `data/blue-fish-ids.json` 不由后台改写。

**验收底线**：首次导入后立即导出，六个文件与当前 `main` 的 `git diff` 为空。不为空就不能上线。

## 5. 后台界面

后台基于 Payload 3，用自定义视图替换默认首页，默认集合列表保留作兜底。

| 页面 | 功能 |
|---|---|
| 概览 | 各渠道待发布数、待发布改动数、最近一次发布结果、“发布”按钮、“立即同步投稿”按钮。 |
| 投稿审核 | 按渠道分页签（全部、网页、GitHub、QQ），卡片网格看图，点开大图和 AI 结论。可就地改名称、角色、分类、标签；可“移除”，可批量移除。AI 拒绝或转人工的条目单独一栏，可“收录”为待发布。 |
| 作品库 | 按渠道、角色、分类、状态筛选并搜索。可多选批量改分类、隐藏、恢复、删除、加入专题。 |
| 专题 | 专题列表与编辑页：三语名称和简介、封面选择、作品搜索勾选、拖动排序、草稿或上线。 |
| 发布 | 本次将发布的变更清单（新增、修改、隐藏、删除、专题），确认后发布；历史批次与日志。 |
| 机器人 | 机器人账号列表、启用或停用、重置 API Key。 |

样式沿用站点蓝色主色，卡片网格为主，操作按钮固定在批量操作栏。

## 6. 发布流程

1. 站长点“发布”，或 Hermes 用 API 发起发布；后台创建 `publish-runs` 记录，写请求文件。
2. 执行器取得发布锁，拉取两个仓库的 `origin/main`，确认工作树干净。
3. 把新作品原图写入内容仓 `dist/submissions/originals/<角色>/<sha前16位>.<扩展名>`；删除的作品从内容仓移除原图和派生图。
4. 从 Payload 导出 `data/*.json`，运行 `tools/prepare_works.mjs` 与派生图脚本，本地构建校验。
5. 只按白名单逐个 `git add`，提交并推送两个仓库。
6. 运行 `ops/deploy-server.sh` 副本，健康检查失败自动回滚。
7. 成功后回写 Payload：状态、`slug`、派生图路径、`needsPublish`、发布批次；把对应中转条目标成 `published`；运行 `ops/issue-reconcile.mjs`。
8. 失败时不改作品状态，记录错误，下次可安全重跑。

旧的 `ops/publish-batch.mjs` 不再作为发布入口，其中的图片校验、提交和部署函数由执行器复用。

## 7. 机器人接入

- Hermes 的 `dafeiyu-publish` 定时任务改为调用后台发布 API。发布有变更时输出摘要，由 Hermes 投递到站长的飞书私信；没有变更时不输出。
- `dafeiyu-review-cycle` 的审核来源加上 `qq`。
- `server/` 删除 `astrbot` 审核身份和 `SUBMISSION_ASTRABOT_REVIEW_TOKEN`。
- 机器人 API 说明见 `admin/README.md` 的“机器人 API”一节。
