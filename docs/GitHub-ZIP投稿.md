# GitHub Issue ZIP 图片集投稿

对应内容仓 Issue [#134](https://github.com/lmy414/ai-girl-stickers/issues/134)，修复 [#133](https://github.com/lmy414/ai-girl-stickers/issues/133) 使用 `/user-attachments/files/` 上传 ZIP 后被误判为没有图片的问题。本文描述代码行为；合并、服务器更新和重新接收分别核验，不能由本地测试推断已经上线。

## 接收与审核

GitHub Issue 正文中的普通图片附件和文件附件共用 URL 识别及下载白名单。附件请求不携带 GitHub API token，每次重定向都重新核对 HTTPS、域名与路径，下载字节和响应体耗时均受限。

ZIP 仅作为容器：先在内存中验证整个包的结构、成员路径、大小、压缩比、CRC、文件头及图片扩展名一致性。所有成员通过后才逐张调用现有 `queue.enqueue`，状态仍是 `received`。原图按 SHA-256 写入私有队列，不按 ZIP 文件名建立磁盘路径，不保存可供发布的压缩包。

每张独立图片继续由现有 Hermes 审核 AI 领取、看图、判断内容、补全文案和翻译。**不新增默认人工审核，也不在 ZIP 接收代码里调用发布。** 只有 AI 无法判断的内容按现有规则进入人工复核，技术错误沿用现有重试机制。审核及发布权限、状态机和定时任务保持原状。

维护者 `tools/intake/cli.mjs pull-issues` 共用解包校验，但保持原来的中转语义：输出 `staged`，不会变成 `ready`，不代替统一队列的 AI 初审。线上补接收应使用 `server/cli.mjs`。

## 固定上限

| 项目 | 上限 |
| --- | --- |
| ZIP 下载大小 | 32 MiB |
| 包内图片数量（去重前） | 100 张 |
| 全部目录与文件条目 | 200 个 |
| 单张图片 | 16 MiB；现有投稿配置更小时取较小值 |
| 解压总量（去重前） | 64 MiB |
| 单成员解压量与压缩量之比 | 200 倍 |

支持经典单卷 ZIP 的 STORE 和 DEFLATE，以及 PNG、JPG/JPEG、GIF、WebP、APNG。支持子目录、UTF-8 文件名及常见 Windows 中文文件名。ZIP64、分卷、自解压包、密码/加密、未知压缩算法、嵌套压缩包、非图片、空图片、符号链接和设备文件均拒绝。README、SVG 等也不能放在包内。

路径包含 `..`、绝对路径、反斜杠、驱动器/流分隔符或控制字符时拒绝。成员名在 Unicode NFC 归一和忽略大小写后重复也拒绝。不同文件名但图片内容相同的情况允许提交，由现有 SHA-256 索引合并，同一图片不重复审核或占用原图空间。不同图片只要字节不同仍分别审核，不引入感知去重。

任一成员不合法时整包拒绝，避免静默丢掉部分图片。解压时同时限制实际输出量，不只相信 ZIP 声明的大小；本地文件头、中央目录、描述符及物理数据范围必须一致，拒绝重叠或隐藏条目。

## 幂等、失败与 Issue 对账

ZIP 成员的来源键为 `github:<repo>#<issue>:<附件ID>:zip:<包SHA256>:<图片数>:<成员序号>`。每个来源键都带完整图片数，队列按图片 SHA 去重时仍保留全部来源键。因此同包重复图片、跨 Issue 或跨渠道重复图片都能核对。全包已经入队时不再下载；磁盘写入中断后可重拉补齐。

只要一张图尚未完成审核/收录、成员没有全部入队、或 ZIP 下载/安全检查失败，Issue 对账脚本保持开启。不会再因为 `/files/` 链接而回复“未检测到图片附件”。整轮存在附件失败时不推进增量游标，下一轮重试。安全检查失败记录在拉取结果/日志中，需要提交者修正包后继续接收；程序不会执行包内文件或让模型绕过这些限制。

全部成员有可核实的已发布页面或审核拒绝结果后，才逐张汇总并关闭 Issue。旧“没有图片”的系统标记不再被复用为新结果，恢复投稿后可追加真实结果。ZIP 在多图 Issue 中作为多个图片成员计数，普通单图的来源键和审核行为不变。

## #133 补接收顺序

1. 合并代码后，服务器按现有发布流程从 GitHub 拉取；更新投稿服务及 Issue 对账脚本到同一版本，重启长驻投稿进程。确认拉取任务与 Hermes 审核任务仍使用原来的私有队列。不需要创建新审核 AI、数据库迁移或新发布入口。
2. 服务端验证完成后再合并内容仓的 ZIP 模板说明，避免对外宣布一个尚未生效的入口。
3. 在已加载生产投稿环境的服务器执行：

   ```bash
   node server/cli.mjs pull-issues --issue 133
   ```

   定向模式可读取 Closed Issue，仍要求 `sticker-submission` 标签，不移动增量游标。无需要求投稿者重新上传，也无需提前重新打开 Issue。
4. 通过已鉴权的队列读取接口回读结果，核对全部成员来源键、图片 SHA 和审核状态。2026-10-24 本地验证原附件得到 **18 张、10,075,739 字节**；原 ZIP 为 10,050,653 字节，SHA-256 为 `4849bbe102503ff6e5a850d8ccaa422ce9b7ea029d78042073661a1b663a0920`。这只是接收兼容与字节校验的基线，不代表内容已经通过线上 AI 审核。
5. 确认完整接收后再重新打开 #133，补充说明旧回复是 ZIP 接收能力缺失造成。让原 Hermes AI 逐张处理，后续按真实审核/上线结果回复；仍有失败时说明失败阶段，不宣称已收录。

当前网站单图表单不增加 ZIP 输入，本改动优先覆盖 GitHub Issue 渠道。
