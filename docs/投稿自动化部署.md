# 投稿自动化部署

面向服务器维护者。描述把私有中转区里**已就绪**的投稿，按批次自动推进到线上的 `ops/publish-batch.mjs`，以及配套的 systemd 定时任务与私有环境变量。

文中只写**变量名**，不写真实域名、IP、凭据或服务器绝对路径；这些值由维护者在服务器侧的环境文件里提供。目录布局与回滚约定仍以 [`../archive/2026-09-24/docs/维护与发布.md`](../archive/2026-09-24/docs/维护与发布.md)（归档，发布拓扑）和 `ops/deploy-server.sh` 的实际行为为准。

## 1. 这个任务做什么

```text
INTAKE_ROOT/meta/<sha256>.json   status=ready
        │  由 server/ 初审通过后的桥接步骤写入（不在本脚本范围内）
        ▼
校验图片 / SHA-256 / 角色 / 分类 / 完整 AI 内容
        ▼
写内容仓原图 → 更新站点仓 data/works.json
        ▼
prepare_works → generate_image_derivatives → 模板校验 → 本地构建校验
        ▼
显式列文件提交（两个仓）→ 推送 → ops/deploy-server.sh → 健康检查
        ▼
成功后才把中转条目置为 published（条目保留，不删除）
```

它**只处理 `status=ready` 的条目**。下架、删除、署名更正永远走人工流程，不在这条链路上。

## 2. 安全边界（先看这一节）

| 规则 | 行为 |
| --- | --- |
| 默认 dry-run | 不写两个工作树、不提交、不推送、不部署、不标记 |
| 总开关 | 只有 `AUTO_PUBLISH_ENABLED=true` 才允许写工作树并本地提交 |
| 推送开关 | 还要 `PUBLISH_PUSH_ENABLED=true` 才 `git push` |
| 部署开关 | 还要 `PUBLISH_DEPLOY_ENABLED=true` 才调用发布脚本 |
| 标记条件 | 推送 + 部署都开启且部署健康检查通过，才把条目标成 `published` |
| 暂存模式 | 只开总开关：写入并本地提交，但不推送、不部署、**不标记**，下次可重跑 |
| 提交方式 | 只 `git add -- <逐条路径>`，绝不 `git add -A` / `git add .` |
| 白名单 | 站点仓仅允许 `data/works.json`、`data/blue-fish-ids.json`、`data/blue-fish-classification.json`；内容仓仅允许原图与派生图前缀。出现白名单外改动或删除即中止 |
| 失败保留 | 任一步失败都不标记 `published`，只写失败批次日志；下次可安全重跑 |
| 不删除 | 不删原图、不删中转条目、不删任何 release / `shared/data` / `acme` |

## 3. 前置条件

- 服务器安装 `node`（>= 18，仓库 `engines` 要求）、`git`；
- **`python3` 且带 Pillow**：派生图脚本 `tools/generate_image_derivatives.py` 依赖 Pillow。任务的预检会先跑 `python3 -c "import PIL"`，缺失时直接失败，不会写坏清单；
- 两个 Git 工作树：本仓库（`SOURCE_DIR` / `PUBLISH_SITE_DIR`）与内容仓（`PUBLISH_CONTENT_DIR`），都能 `git fetch` / `git push`；
- 私有中转区 `INTAKE_ROOT`：必须在两个公开仓之外，且不在任何 git 工作树内（与 `tools/intake/core.mjs` 的检查同一口径）；
- 部署脚本所需的 `DEPLOY_ROOT`、`HEALTH_URL` 等（见 `ops/deploy-server.sh` 头部与归档文档 §3.1）。

## 4. 环境变量

完整模板见 [`../ops/publish-batch.env.example`](../ops/publish-batch.env.example)。

必填：

| 变量 | 说明 |
| --- | --- |
| `INTAKE_ROOT` | 私有中转区根；读 `meta/`、`inbox/`，批次日志写 `batches/` |
| `PUBLISH_CONTENT_DIR` | 内容仓工作树（也可用 `INTAKE_CONTENT_DIR` / `CONTENT_DIR`） |
| `PUBLISH_SITE_DIR` | 站点仓工作树；默认是脚本所在仓库根 |

开关（默认全关）：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `AUTO_PUBLISH_ENABLED` | `false` | 允许写工作树并本地提交 |
| `PUBLISH_PUSH_ENABLED` | `false` | 允许 `git push` |
| `PUBLISH_DEPLOY_ENABLED` | `false` | 允许调用发布脚本 |

常用可选项：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `PUBLISH_REMOTE` / `PUBLISH_BRANCH` | `origin` / `main` | 推送目标 |
| `PUBLISH_NODE` / `PUBLISH_PYTHON` | `node` 可执行文件 / `python3` | 工具链解释器 |
| `PUBLISH_BUILD_CHECK` | `true` | 提交前在临时目录再跑一次完整构建校验 |
| `PUBLISH_ORIGINAL_BASE_URL` | 内容仓 raw 基址 | 新记录 `path` 的基址，不要带结尾斜杠 |
| `PUBLISH_MIN_CONFIDENCE` | `0.6` | AI 置信度门槛，低于它整条留在 ready |
| `PUBLISH_MAX_ENTRIES` | `0`（不限） | 单批次最多处理多少条 |
| `PUBLISH_GIT_NAME` / `PUBLISH_GIT_EMAIL` | 机器人身份 | 提交作者 |
| `PUBLISH_LOCK_STALE_MS` | `21600000`（6 小时） | 发布锁陈旧阈值 |
| `PUBLISH_DEPLOY_ROOT` | 无 | 部署脚本副本所在发布根（推荐） |
| `PUBLISH_DEPLOY_CMD` | 无 | 自定义部署命令，用 `bash -lc` 执行 |

部署配置（`PUBLISH_DEPLOY_ENABLED=true` 时）：`PUBLISH_DEPLOY_ROOT` 优先；脚本会把 `ops/deploy-server.sh` 复制成 `$PUBLISH_DEPLOY_ROOT/.publish-deploy-runner.sh` 再执行，避免 `reset --hard` 替换正在运行的脚本。也可以直接用 `PUBLISH_DEPLOY_CMD` 或 `PUBLISH_DEPLOY_RUNNER`。`deploy-server.sh` 自己需要的 `DEPLOY_ROOT`、`REPO_URL`、`BRANCH`、`HEALTH_URL`、`CONTENT_REPO_URL`、`CONTENT_BRANCH`、`CONTENT_DIR` 等，一并放进同一个私有环境文件（环境变量优先于 `DEPLOY_ENV` 文件）。

## 5. 先 dry-run 验证

默认就是 dry-run。在服务器上先手动跑一次，确认计划与路径无误：

```bash
sudo -u dafeiyu env $(grep -v '^#' /etc/dafeiyu/publish.env | xargs) \
  node "$SOURCE_DIR/ops/publish-batch.mjs" --json
```

dry-run 只读中转区与清单，打印：可发布条目、将被识别为重复的条目、因校验不过而保留的条目及原因，以及开关状态。**它不会写任何文件。** 需要机器可读结果时加 `--json`。

其他入口：

```bash
node ops/publish-batch.mjs --dry-run     # 即使开关都开也强制演练
node ops/publish-batch.mjs --live        # 需要 AUTO_PUBLISH_ENABLED=true
node ops/publish-batch.mjs --limit 5     # 本次最多处理 5 条
node ops/publish-batch.mjs --help
node --test ops/tests/publish-batch.test.mjs   # 或 npm run test:publish
```

## 6. 安装 systemd 定时任务

单元文件在 `ops/systemd/`：`dafeiyu-publish.service` 与 `dafeiyu-publish.timer`。

```bash
sudo install -m 0644 ops/systemd/dafeiyu-publish.service /etc/systemd/system/
sudo install -m 0644 ops/systemd/dafeiyu-publish.timer   /etc/systemd/system/
# 私有环境文件（不进 git），权限收紧
sudo install -m 0600 -o root -g root /dev/null /etc/dafeiyu/publish.env
sudo editor /etc/dafeiyu/publish.env
sudo systemctl daemon-reload
sudo systemctl enable --now dafeiyu-publish.timer
systemctl list-timers dafeiyu-publish.timer      # 核对下次触发时间
```

unit 里的 `User=` / `Group=` / `EnvironmentFile=` / `ExecStart=` 路径按服务器实际部署调整；`SOURCE_DIR` 由环境文件提供，`ExecStart` 用 `${SOURCE_DIR}` 展开。

### 定时规则与时区

`OnCalendar=*-*-* 00/6:00:00` 表示每 6 小时整点，即本地时间 **00:00、06:00、12:00、18:00**。`OnCalendar` 用系统本地时区，因此服务器必须设成 `Asia/Shanghai`：

```bash
timedatectl set-timezone Asia/Shanghai
timedatectl status
```

`Persistent=true` 让关机期间错过的窗口在开机后补跑；`RandomizedDelaySec=300` 给 0–300 秒随机延迟，避开其它整点任务。任务单次可能跑构建 + 部署，`TimeoutStartSec=3600` 已放宽。

## 7. 失败与恢复

- **任一步失败**：非零退出，条目保持 `ready`，只写失败批次日志，线上不变；
- **批次日志**：`INTAKE_ROOT/batches/<批次号>.json`，记录本次计划写入的文件、提交、推送与部署状态。失败日志用于下一次的**受控回收**；
- **工作树回收**：live 开始时会 `git fetch`，若工作树有改动或 `HEAD` 落后/超前：
  - 只有改动能对上「上一次未完成批次」记录的路径（或发布白名单）时，才 `git reset --hard origin/<branch>` 并清掉日志里未跟踪的残留；
  - 出现计划外改动（尤其没有批次日志时）一律中止，**绝不替人 reset**；
- **重复运行**：同图已按 `sha256` 在清单里 → 直接标记为 `published`，不重复写清单；
- **部分成功**：不会把任何条目误标记为已发布；下一次批次会从头重算（幂等）；
- **发布锁**：`INTAKE_ROOT/logs/publish.lock` 跨进程互斥，超过 `PUBLISH_LOCK_STALE_MS`（默认 6 小时）自动回收，避免进程被杀后永久卡死。

## 8. ready 条目与 AI 内容校验

转发区 `meta/<sha256>.json` 里 `status=ready` 的条目才会被处理。它由 `server/bridge.mjs` 调用 `tools/intake/core.mjs` 的 `stageReadyItem` 写入，形状为：`content`（六个 AI 字段）、`fields`（含 `character`/`tags`）、`origin`、`license`（字符串或对象）、`receivedAt`、`submissionId`、`contentSchema`。发布器按下表校验；**任一不过整条留在 ready，原因写进摘要**：

| 项 | 要求 |
| --- | --- |
| 图片 | `inbox/<sha256><ext>` 存在、非空，且重算 SHA-256 与记录一致 |
| 扩展名 | `.png` / `.jpg` / `.jpeg` / `.gif` / `.webp` / `.apng` |
| 角色 | `content.characterId`（回退 `fields.character`）能在 `data/characters.json` 的 active 条目里解析到 |
| 分类 | `content.categoryIds` 非空，且每一项都能在 `data/categories.json` 的 active 条目里解析到 |
| AI 内容 | `content` 六字段齐全：`name` / `description` / `commentary` / `characterId` / `categoryIds` / `tags`；`name`、`commentary`、`tags` 非空，tag 不重复 |
| 置信度（可选） | 条目若带 `verdict` / `confidence`，则要求 `verdict=pass` 且 `confidence` 为数字、≥ `PUBLISH_MIN_CONFIDENCE`；不带则以 `status=ready` 为准（桥接只写 `auto_passed`） |
| 文本 | 不超长（上限与 `server/bridge.mjs` 对齐）、不含控制字符、不含 `<` `>` |
| 枚举 | `originType` / `licenseType` 若给出，必须在契约枚举内（缺省记 `unknown`；`removed` 不自动发布） |

字段来源按 `content` → `ai`（或 `review`）→ `fields` 的顺序取第一个非空值；`originType` / `licenseType` 也会从 `origin` / `license` 对象（或 `license` 字符串）里回退。系统字段（`id` / `slug` / 路径 / 尺寸 / 哈希 / 时间戳）一律由程序生成，不由模型覆盖：

- `id` = `sticker_<sha256 前 24 位>`，由内容决定、幂等；
- `slug` 由 `tools/prepare_works.mjs` 按既有规则补全，已发布记录的 `id` / `slug` 冻结不动；
- 原图路径 = `dist/submissions/originals/<characterId>/<sha256 前 16 位><ext>`，发布后不改名、不移动；
- 尺寸 / 动画标记由发布器的零依赖文件头嗅探填入；`thumbnailPath` / `fullPath` 由派生图脚本回填。

## 9. 上架与下架边界

- 自动发布只做**收录**，不处理下架 / 删除 / 署名更正；
- 驳回、低置信度、字段不完整的投稿留在审核区或 ready，不进入批次；
- 已发布条目在中转区被置为 `published` 后会**保留**；确认线上 Raw 已生效后，仍由维护者用 `tools/intake/cli.mjs verify` / `prune --apply` 按回源校验清理；
- 首批数据 `shared/data` 与 release 的删除策略不变，见归档发布文档 §4、§5。

## 10. 本任务不负责的部分

- 不实现「初审判定 → 写中转区」的桥接（在 `server/` 与 `tools/intake/` 侧）；
- 不改 `server/`、`tools/intake/core`、前端页面与生成器；
- 不替代人工看图：新增 `commentary` / `categoryIds` 的正确性由上游 AI 生成与校验把关，发布器只做形式校验；
- 不自动关闭或评论 GitHub Issue；
- 不引入数据库或第三方依赖，只用 Node 标准库 + 现有 Python 工具链。
