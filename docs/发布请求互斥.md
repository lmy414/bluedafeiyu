# 发布请求互斥

后台的 `publish.request` 是一个持久化单槽请求，不是可以覆盖的通知。
并发 HTTP 请求可能同时通过数据库的排队检查，因此最终入队使用同目录临时文件加 `link`。
只有一个请求能占用空槽；冲突请求返回 409，并只结束自己的数据库批次。

后台执行器先获得 `INTAKE_ROOT/logs/publish.lock`，再把请求改名为 `.taken`。
等待期间不修改排队状态、不获取快照、不构建，也不发送失败通知。
默认每 5 秒检查一次，每 5 分钟记录一次；55 分钟后退出 75，原请求仍在。
现有 `PathExists` 会再次拉起执行器，重新按相同间隔等待，不会立即退出形成重启风暴。
这个等待上限必须小于现行服务的 `TimeoutStartSec=3600`。
只要本次启动曾经等待，即使随后获得锁，也会先释放锁、不接管请求并退出 75。
下一次启动重新获取锁后才接管，确保实际发布拥有完整的 60 分钟预算。

锁包含随机 token、PID 和创建时间；Linux 另记录 boot ID 与进程 start time，供人工排查 PID 复用。
释放前核对持有文件的 inode、设备号与 token。所有参与者必须遵守：只释放自己持有的锁，不能替换持有中的锁。
旧版 `{pid, at}` 锁仍会阻止进入。年龄、进程已退出、JSON 损坏都不授权自动删除锁。
因此此版本优先保证互斥和请求保留，不提供死锁自动恢复。不能声称超时后会自动完成发布。

进程在接管前退出：请求继续排队。接管后退出：保留 `.taken`、提交及日志；现有中断恢复只在无锁等安全条件满足时将批次标为中断。
遗留锁会阻止既有中断恢复获取锁，需维护者先核对 PID、boot/start time、服务及其构建子进程，再经审核恢复。
不要按 mtime 删除锁，也不要在新旧发布器正在运行时清理锁。不要把 `.taken` 自动改回排队文件或宣称已发布。

若 Emao 发布需要排除 Blue 发布，必须在整个 Emao 发布操作之前获得同一个 `publish.lock`，结束后释放。
既有 `.deploy.lock` 只覆盖部署，不代替全流程发布锁。顺序固定为发布锁在前、部署锁在后，禁止反过来等待。
两个站点继续使用各自的源码、构建目录与 current；共享的是互斥协议，不是发布产物。
上线时必须确认所有相关执行器使用新协议，不能只更新仓库而遗漏实际服务执行路径。
